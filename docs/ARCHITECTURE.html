Architecture & Technical Plan

How Easyclz is put together

A class-management platform for tuition teachers: four client apps, one Postgres database, and a security boundary that the database itself enforces. This document walks the whole system top-down — the moving parts, why each one exists, and how a request travels through it.

01

System context

Everything is arranged around a single principle: one database of record, many thin clients, and one place where access rules live. There is no bespoke API server to operate. Clients either read straight from Postgres (guarded by row-level security) or call a small serverless function for anything that needs a secret or a server-side check.

03

The Supabase backend

Supabase bundles the pieces a backend needs into one managed project. I use four of them:

  • Postgres — the single source of truth. ~46 tables, ~84 migrations. All business rules that must not be bypassed live here as constraints, triggers, and RLS policies.
  • PostgREST — an auto-generated REST API over the database. Clients read (and do simple writes) through it. Every request runs as the calling user, so RLS decides what comes back.
  • Edge Functions — Deno functions with access to the service_role key. Anything requiring a secret, a third-party call, or a check the client cannot be trusted to do runs here (~70 functions).
  • Auth + Vault — Supabase Auth issues JWTs; a custom hook adds a role claim; Vault stores the one server secret a database trigger needs.
Design rule If a rule can be expressed as an RLS policy or a database constraint, it goes in the database — not in app code, which any of four clients could implement inconsistently or forget.
04

Identity & roles

There are four kinds of user: super_admin, teacher, assistant, student. Supabase Auth only knows "authenticated" — the domain role is layered on top.

A user_roles table maps each auth user to exactly one role. On every token issue or refresh, the custom_access_token_hook reads that row and injects a role claim into the JWT. RLS policies then branch on that claim — is_super_admin(), is_teacher(), and so on — without another database round-trip.

05

The read / write split

This is the single most important idea in the architecture.

Reads — straight through, guarded by RLS

A client asks PostgREST for rows. The request carries the user's JWT. Postgres applies the RLS policies for that user's role and returns only permitted rows. The client cannot ask for more than it is allowed; there is no server code to bypass because the rule is in the database.

Writes that need trust — behind an Edge Function

Creating a teacher, verifying an OTP, charging a card, sending an SMS, opening or grading an exam: these run in an Edge Function holding the service_role key. The function authenticates the caller, runs its own checks, performs the write, and returns a result. The privileged key never leaves the server.

08

Offline sync (teacher app)

Teachers use the app in classrooms with poor connectivity, so it is offline-first: the UI never waits on the network.

  • The phone holds its own SQLite database (Drizzle ORM, its own migration chain).
  • Every screen reads and writes local rows only — instant, works with no signal.
  • A sync engine with three parts — queue, push, pull — reconciles local and server state in the background.
  • It is event-driven: each local write calls scheduleSync(), debounced. A 5-minute foreground timer is only a backstop.
  • Pushes use Postgres upsert with primary-key conflict resolution (merge-duplicates), so replaying the same change is harmless — the sync is idempotent.
  • Auth tokens refresh proactively (5-minute buffer); an expired session surfaces a single clear "log in again".
  • Separately, the app writes AES-GCM encrypted backups (derived key) so a teacher can restore onto a new phone.
09

Notifications

Two channels: Expo Push for the teacher app, Web Push (VAPID) for the student PWA. Some notifications originate from a database change (a payment recorded, a join request answered), so the trigger that fires them needs to authenticate to an Edge Function — which means it needs the service_role key.

Supabase's managed postgres role cannot hold custom settings, so the key is stored in Vault and read at trigger time via vault.decrypted_secrets. The whole path is best-effort: if the key is missing or pg_net is unavailable, the in-app notification row is still saved and the caller's transaction still commits.

10

Payments & subscriptions

Teachers pay a subscription to unlock Pro features. Stripe Checkout handles the card; the platform never sees card data.

  1. create_checkout_session makes a Stripe session and returns its URL.
  2. The teacher pays on Stripe's hosted page.
  3. Stripe calls stripe_webhook; the function verifies the signature, then updates subscriptions and appends to subscription_events.
  4. Pro entitlement is enforced server-side — RLS and function checks read the subscription row, so a patched client cannot unlock anything.
Not in the repo No card numbers, no Stripe secret key, no webhook secret. Those live only in environment variables on the server. The open-source repo ships empty .env.example templates.

13

Security model, in one list

  • RLS on every table. The database is the last line of defence; a bug in a client cannot leak another tenant's data.
  • Role in the JWT. Authorization is a signed claim check, set by a hook, not a value the client sends.
  • Secrets only server-side. service_role key, Stripe keys, SMS keys — environment variables and Vault, never the repo, never a client bundle.
  • Public by design vs. secret. The Supabase anon key ships in every client and is meant to — it only permits what RLS already allows.
  • Rate limits & OTPs for every account-changing action, enforced in Edge Functions with dedicated tables (login_attempts, *_otps, change_rate_limits).
  • Device-aware trials (device_trials) so a new account on a used phone gets no fresh trial.
  • Audit triggers on money and identity tables.
  • Encrypted local backups (AES-GCM) on the teacher app.
